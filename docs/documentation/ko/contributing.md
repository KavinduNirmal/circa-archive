# 기여

하나의 일관된 변경, 그것을 증명하는 검사, 검증한 내용을 밝히는 풀 리퀘스트.

## 시작하기 전에

README.md, AGENTS.md, 변경이 닿는 문서를 읽으세요. 이슈와 풀 리퀘스트를 먼저 검색하세요. 아키텍처, 의존성, 이야기 역학에는 제안을 먼저 열고, 작은 교정은 바로 풀 리퀘스트로 보내도 됩니다.

> [!WARNING]
> 초안은 초안입니다
>
> ARCHITECTURE.md는 만들어지지 않은 플랫폼을 설명하고, 디자인과 제품 문서는 의도를 설명합니다. 코드와 명세가 다르면 조용히 하나를 고르지 말고 이슈에서 말하세요.

## 브랜치당 하나의 변경

포크하고 브랜치를 만들고, 브랜치마다 하나의 변경만 유지하세요. docs/record-lifecycle과 feat/record-editor가 예시 형태입니다. 리팩터와 동작 변경을 섞지 마세요.

- 잠금 파일을 커밋하고, 경쟁하는 패키지 관리자 잠금 파일을 추가하지 마세요.
- 로컬 환경 파일, 자격 증명, 생성된 출력, 편집기 설정을 커밋하지 마세요.
- 작성자 크레딧, 안정적인 ID, 표시 코드를 보존하세요.

동작 변경에는 테스트를 먼저 쓰세요. red, green, refactor. 커버리지 기준은 없으며, 문장 대신 키를 검증하는 테스트는 없는 편이 낫습니다.

## 검사

풀 리퀘스트를 열기 전에 변경한 부분을 실행하세요. 전체 통과는 훅입니다.

```sh
bun run check
bun run test
bun run check:client
bun run precommit
```

훅은 스테이징된 README를 확인한 뒤 루트 도구 테스트와 프런트엔드 린트, 타입 검사, 단위 스위트를 실행합니다. 실패는 검사가 작동한 것입니다. 우회하지 말고 고치세요.

## 문서도 변경의 일부입니다

문서는 코드와 함께 바뀝니다. 모든 작성 폴더에는 README가, 모든 사용자 노출 문자열에는 언어별 키가, 새 동작에는 프로젝트 방식의 테스트가 필요합니다.

- 새 카피: 영어에 키를 추가하고, 한국어를 번역한 뒤 카탈로그 테스트를 실행하세요.
- 새 폴더: README.md를 추가하고 스테이징하세요.
- 새 인터페이스: 데스크톱과 모바일 너비의 스크린샷을 풀 리퀘스트에 넣으세요.
- 변경된 라우트: 메타데이터와 테스트가 붙드는 모든 링크를 갱신하세요.

## 커밋과 풀 리퀘스트

명령형 커밋 메시지를 쓰세요. 예: Add record creation endpoint. 풀 리퀘스트에는 문제, 결과 동작, 관련 이슈나 명세, 실제로 검증한 내용을 적으세요.

기여자 라이선스 계약은 필요하지 않습니다. MIT로 라이선스할 수 있는 작업만 제출하고, 제3자 자료를 밝히세요.
